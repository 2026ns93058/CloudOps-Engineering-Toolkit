# Data Model: Kubernetes Manifest Review Assistant

## 1. Overview

This document defines the data structures used by the Kubernetes Manifest Review Assistant.

The data model covers:
- Parsed Kubernetes resources.
- Supported and unsupported resources.
- AI-generated review findings.
- Review reports.
- Evaluation cases.
- Evaluation results.

The Python application MUST validate all model-generated data before accepting it.

## 2. Enumerations

### 2.1 Finding Severity

Allowed values:

- `Critical`
- `High`
- `Medium`
- `Low`
- `Info`

Severity represents the potential impact of an observed configuration issue.
It MUST be assigned based on the evidence in the manifest, considering
potential impact, scope, and the degree of risk demonstrated by the
configuration.

The following risk-based rubric MUST be applied consistently:

| Severity | Assessment criteria |
|---|---|
| `Critical` | Extreme potential impact, such as catastrophic security compromise or major service disruption with broad consequences. Requires strong evidence of the severity and scope of the risk. |
| `High` | Significant security exposure or operational risk that could substantially compromise a workload or its environment. |
| `Medium` | Meaningful security, reliability, configuration, or resource-management weakness that requires corrective action but has more limited potential impact. |
| `Low` | Relatively minor weakness with limited potential consequences or reduced likelihood of causing harm. |
| `Info` | Informational observation or improvement opportunity without a demonstrated material risk. |

Severity assessment rules:

- Assess the actual configuration and its demonstrated potential impact.
- Consider the scope of the affected resource and the degree of exposure.
- Do not assign `Critical` solely because a finding belongs to the Security category.
- Do not infer runtime exposure, successful exploitation, or host or cluster compromise from static YAML alone.
- Assign a higher severity only when the available manifest evidence supports it.
- When evidence is insufficient to justify a higher severity, select the lower severity supported by the evidence.
- Severity is an AI-generated assessment and MUST be evaluated independently against the expected severity or permitted severity range.

The model MUST NOT assign a severity outside the allowed values.

### 2.2 Finding Category

Allowed values:

- `Security`
- `Reliability`
- `Configuration`
- `Resource Management`

Every finding MUST belong to exactly one allowed category.

## 3. Kubernetes Resource Identity

Represents a Kubernetes resource extracted from a YAML document.

| Field | Type | Required | Description |
|---|---|---|---|
| api_version | string | Yes | Kubernetes API version |
| kind | string | Yes | Resource kind |
| name | string | Yes | Resource metadata.name |
| namespace | string or null | No | Resource namespace |
| document_index | integer | Yes | Zero-based YAML document position |
| supported | boolean | Yes | Whether the resource kind is supported |

Rules:
- `api_version`, `kind`, and `name` MUST be present and non-empty.
- `document_index` MUST be a non-negative integer.
- Resource identity MUST be derived from the submitted YAML, not invented by the model.
- Unsupported resource kinds MUST be represented explicitly.

## 4. Review Finding

Represents one issue or observation generated by the AI review.

| Field | Type | Required | Description |
|---|---|---|---|
| finding_id | string | Yes | Unique finding identifier |
| issue_id | string or null | Yes | Controlled stable issue identifier for a recognised issue; null for unknown or unexpected findings |
| severity | string | Yes | Critical, High, Medium, Low, or Info |
| category | string | Yes | Security, Reliability, Configuration, or Resource Management |
| resource_kind | string | Yes | Kubernetes resource kind |
| resource_name | string | Yes | Resource metadata.name |
| title | string | Yes | Short issue description |
| explanation | string | Yes | Explanation of the observed issue or potential risk |
| evidence | object | Yes | Manifest-grounded evidence |
| remediation | string | Yes | Actionable recommendation |

### Evidence Object

| Field | Type | Required | Description |
|---|---|---|---|
| field_path | string | Yes | Relevant YAML field path |
| observed_value | string or null | Yes | Sanitised observed value or null if absent |
| observation | string | Yes | What the manifest demonstrates |

Rules:
- Evidence MUST refer to a real field or missing field in the submitted resource.
- Evidence MUST NOT contain original Kubernetes Secret values.
- Evidence MUST NOT claim runtime behaviour that cannot be established from static YAML.
- `observed_value` MUST contain sanitised information only.

### Finding Identity Rules

- Every finding MUST have a unique `finding_id` within its review.
- `issue_id` is a required field that may contain a stable identifier or null.
- Known issue identifiers MUST come from a controlled issue catalogue defined by the application and evaluation dataset.
- The model MUST NOT invent a known issue identifier.
- Unknown or unexpected findings MUST use `issue_id: null`.
- Duplicate findings for the same issue and resource MUST be rejected or reported as duplicates.

## 5. Review Report

Represents the complete response returned by the AI review application.

| Field | Type | Required | Description |
|---|---|---|---|
| review_summary | string | Yes | Overall review explanation |
| resources_reviewed | array | Yes | Supported resource identities reviewed |
| unsupported_resources | array | Yes | Unsupported resource identities |
| findings | array | Yes | Review findings |
| model_metadata | object | Yes | Trusted model execution information attached by the application |

### Model Metadata

The application MUST attach the following trusted metadata after a successful model execution.

| Field | Type | Required | Description |
|---|---|---|---|
| provider | string | Yes | AI runtime provider, such as Ollama |
| model | string | Yes | Actual model name and tag |
| prompt_version | string | Yes | Version of the prompt used |
| temperature | number | Yes | Actual configured generation temperature |
| duration_ms | integer | Yes | Actual model execution duration in milliseconds |

For failed model executions, the application MUST record the available execution context and the failure separately. It MUST NOT invent missing metadata values.

Model metadata MUST reflect actual execution settings.

The model MUST NOT be allowed to invent its own metadata. The application MUST attach trusted execution metadata.

## 6. Evaluation Case

Represents one input scenario in the fixed evaluation dataset.

| Field | Type | Required | Description |
|---|---|---|---|
| case_id | string | Yes | Unique evaluation case identifier |
| description | string | Yes | Scenario description |
| category | string | Yes | Evaluation scenario category |
| input_manifest | string | Yes | YAML input or deliberately malformed input |
| expected_outcome | string | Yes | Expected application behaviour |
| expected_findings | array | Yes | Expected issue definitions |
| expected_resources | array | Yes | Expected resource identities |

An expected finding MUST define:
- Stable `issue_id`.
- Expected resource kind and name.
- Expected category.
- Expected severity or permitted severity range.
- Required evidence field path or evidence condition.
- Expected remediation characteristics.

The evaluation dataset MUST contain at least 15 meaningful cases.

## 7. Evaluation Result

Represents the result of evaluating one case.

| Field | Type | Required | Description |
|---|---|---|---|
| case_id | string | Yes | Evaluation case identifier |
| application_status | string | Yes | Application execution outcome |
| schema_pass | boolean | Yes | Whether output schema passed |
| invariant_pass | boolean | Yes | Whether structural and safety invariants passed |
| semantic_score | number or null | Yes | Semantic score where applicable |
| expected_issue_count | integer | Yes | Number of expected issues |
| matched_issue_count | integer | Yes | Number of matched expected issues |
| precision | number or null | Yes | Issue-identification precision (0–100) |
| recall | number or null | Yes | Issue-identification recall (0–100) |
| f1 | number or null | Yes | Issue-identification F1 score (0–100) |
| severity_score | number or null | Yes | Severity correctness score (0–100) |
| evidence_score | number or null | Yes | Evidence grounding score (0–100) |
| remediation_score | number or null | Yes | Remediation quality score (0–100) |
| false_positive_count | integer | Yes | Unsupported findings |
| duplicate_count | integer | Yes | Duplicate findings |
| errors | array | Yes | Error descriptions |
| case_pass | boolean | Yes | Final case outcome |

Application status values:

- `SUCCESS`
- `INPUT_REJECTED`
- `MODEL_ERROR`
- `OUTPUT_INVALID`
- `EVALUATION_ERROR`

A model execution failure MUST NOT be misreported as a successful review.

## 8. Aggregate Evaluation Report

Represents the complete harness run.

Required fields:

- `run_id`
- `started_at`
- `completed_at`
- `model_metadata`
- `dataset_version`
- `total_cases`
- `completed_cases`
- `failed_cases`
- `schema_pass_rate`
- `invariant_pass_rate`
- `semantic_score`
- `acceptance_threshold`
- `overall_status`
- `case_results`

`overall_status` MUST be either `PASS` or `FAIL`.

Acceptance rules:
- Semantic score MUST be at least 80%.
- Schema validation MUST achieve 100% compliance for accepted model responses.
- Safety and invariant checks MUST achieve 100% compliance.
- A model execution failure MUST be recorded separately and MUST NOT be silently omitted from the evaluation report.
- Missing evaluation results MUST NOT be counted as passing cases.

## 9. Data Validation Rules

The application MUST enforce:

1. All required fields are present.
2. Field types match the documented contract.
3. Severity and category values belong to their allowed enumerations.
4. Resource identities match resources parsed from the submitted manifest.
5. Evidence is grounded in the sanitised manifest.
6. Secret values are never included in model requests or stored evidence.
7. Finding identifiers are unique within a report.
8. Duplicate expected issues cannot receive multiple scoring credits.
9. Evaluation case identifiers are unique.
10. Evaluation results retain failures and errors.

## 10. Data Persistence

The application will not require a database.

- Input manifests remain at their original locations.
- Review reports may be written to a user-specified JSON output file.
- Evaluation dataset is stored in `evals/dataset.json`.
- Evaluation results are stored in `artifacts/`.
- Harness execution logs are stored in `evidence/`.
- Original Secret values MUST NOT be copied into generated reports or evidence.

## 11. Data Model Limitations

- Resource identity does not prove that a resource is valid against a live Kubernetes API server.
- Evidence represents static YAML observations only.
- A finding represents a potential issue, not proof of an actual runtime failure.
- Severity is an AI-generated assessment and must be evaluated independently.
- Semantic matching is based on stable expected issue identifiers and resource identity rather than exact natural-language equality.
